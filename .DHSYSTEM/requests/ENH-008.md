# ENH-008 — Bounded HTTP timeouts for provider calls

- Type: ENH
- Priority: P2
- State: open
- Source: vp-audit Tier 3, 2026-10-22
- References: `videotrans/recognition/`, `videotrans/translator/`, `videotrans/tts/`, `videotrans/task/update_ffmpeg.py`

## Evidence

An AST scan found 34 `requests.*` calls without a `timeout` argument, for example `recognition/_ai302.py:44`, `recognition/_openrouter.py:55`, `recognition/_recognapi.py:163`, `translator/_google.py:48`, `translator/_baidu.py:36`, `tts/_minimaxi.py:60` and `task/update_ffmpeg.py:29`. Without a timeout, a stalled remote endpoint blocks the stage worker `QThread` (`task/job.py`) indefinitely, and the user's Stop action only takes effect between queue items.

Related low-severity findings from the same scan:

- `util/help_misc.py:145` uses `shell=True` for the macOS shutdown command (constant string, so not injectable, but unnecessary).
- 28 `except Exception: pass` blocks and bare `except:` at `sp.py:60` and `process/signelobj.py:80` hide failures.

## Acceptance

Every outbound provider HTTP call has a bounded connect/read timeout (upload/long-poll calls may use a longer read timeout), timeouts surface as the existing provider error path, and a regression test or lint check prevents new unbounded calls.
